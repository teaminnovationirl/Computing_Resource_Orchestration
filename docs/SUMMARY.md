## Gotchas and open items

- For E2-3: submit() already pushes into `self.queue` between its log line and its job_state event (D-105): add the loop wake after the job_state hook. A job leaves the queue only by `remove()` after Committed (or a cancel). A queued job larger than the current allocatable maximum (capacity.py run after it was submitted) never fits and would block the FCFS head forever.
- For E2-3 and E2-4 (D-104): take `self.lock` before any tx() and hold it across a whole cycle, requeue or cancel; nothing may wait for it under a database lock, and engine calls under it return at once. capacity_changed() runs in an after_commit hook on the thread that called release() (E1's supervisor or cancel, E4's recovery executor, startup reconciliation): it only sets the wake Event, never runs a cycle and never takes the lock (D-75). first_fit's predicate must be pure (Snapshot.fits on the cycle's snapshot). Each slice needs a test where an admission cycle, a cancel and a release run at once, finish within a timeout and leave the invariants clean. Log how long a cycle holds the lock: submit's push hook waits for it, and CPython locks are not fair.
- For E2-4: requeue pushes a QueueEntry built from the locked row (same submitted_at, so it returns to its arrival place); rebuild() pushes the queued rows in (submitted_at, job_id) order (O(1) appends) before the API takes submits, or a startup submit and rebuild() push one job twice (ValueError). Between COMMIT and the push a job is queued in the database but not yet in memory: cancel_queued decides by the row, not by queue membership alone. A lost COMMIT acknowledgement leaves a committed job out of the queue until rebuild() (D-105): pick a reconcile of queued rows missing from the queue or a lookup by payload_path.
- For E4-3: build `SubmitRequest` with `source_name` from the multipart file name; parse form integers strictly, pass None for an absent or empty field, and turn a parse failure into 400 {field, error}, never FastAPI's 422; map ApiError to its status and anything else to a generic 500. Uploads are spooled (D-90): stream each upload into `DATA_DIR/spool`, reading at most the type's cap plus one byte and never holding it whole in memory, pass submit() that file's Path (E2-5), and delete a spool file still there after submit() returns or raises.
- For E2-5 (D-90, D-96): `E2Port.submit(user, req, source: Path)`. Refuse (ValueError, nothing written) a path that does not resolve inside `DATA_DIR/spool`, validate it in chunks (zipfile by path) and `os.replace` it into `payloads/<hex>/<stored name>`; spool and payloads share a drive, so the move is a rename, never a copy; create the spool folder in both reset scripts. Adapt the E2-1 tests to pass spooled files, with the same checks and the same expected results. stdin: at most 1 MiB, code_run only, stored as `input.txt` beside the source (E1-1 then finds two files in a code_run payload); seed row code_run (need class 3, max_time_limit_s 10).
