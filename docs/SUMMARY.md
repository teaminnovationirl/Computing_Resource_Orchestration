## Gotchas and open items

- For E4-3 and X-1 (D-122): `e2.cancel_queued(job_id, by)` returns True once cancelled; raises IllegalTransition ("being admitted ... try again") for a job that reads admitted: answer 409 and let the user retry, never 202; returns False for any other state: then try e1.cancel. After a raise of any other kind, a job that now reads cancelled was cancelled (a lost acknowledgement). queue_view() gives QueueEntry only: position is the index + 1, the wait clock.time() - submitted_at (D-126). The admission state (paused, reason, policy, in_doubt) reaches pages only through admission events (D-123): no port reads it, so an admin status endpoint needs an E2Port getter (a proposal for the owner).
- For E4-3: build `SubmitRequest` with `source_name` from the multipart file name; parse form integers strictly, pass None for an absent or empty field, and turn a parse failure into 400 {field, error}, never FastAPI's 422; map ApiError to its status and anything else to a generic 500 that never echoes the exception text. Uploads are spooled (D-90, D-128): stream each upload directly into `DATA_DIR/spool` under a server-made name (never the user's file name, D-76), reading at most the type's cap plus one byte and never holding it whole in memory; close the file (on Windows os.replace fails on an open one), pass submit() its Path, and delete a spool file still there after submit() returns or raises. A ValueError from submit() is a caller bug. Pass stdin as bytes or None (only code_run takes one); its 1 MiB cap is E2's STDIN_MAX_BYTES: move it to Config when E4-3 reads it, since no engine may import E2's validation.
- For E1-2, the calls (D-142): new_run() comes before anything else can end the attempt and before start(); payload(file_ref, with_input=type_code == "code_run"); one case() per test_cases row, read once and kept for judge_cases(); SandboxSpec(job_dir=payload.folder, or run.job after extract_zip(), out_dir=run.out); the worker's spec is run.spec and holds input paths only. The worker prints the oom line for OutOfMemory and the error line for SandboxError and OSError. After the confirmed stop the supervisor calls judge_cases(), exited() or write_result(), and remove_unpacked(run.job) (up to 4 GiB lie there), also after a failed start. make_job's payloads/test is not a payload E1 accepts.
- For E1-2, the fake sandbox: FakeRunner keeps its sandboxes in its process, so SANDBOX_BACKEND=fake needs the thread launcher. A stop or remove makes the exec in progress raise SandboxError in the worker's thread, which the supervisor, having set its flag, ignores.
- For E1-2, python_ml: unpack before start(), so before the deadline runs: in a child process that the supervisor can kill, or at most one at a time (it is Python's own CPU: 3.5 s for a hostile 5 MB archive, more for 4 GiB). BadArchive's text may be shown to the student.
