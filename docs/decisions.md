# Decisions

D-01 to D-17 are in docs/IMPLEMENTATION_PLAN.md section 17. D-18 to D-30 are proposals in docs/LAN_BUILD_GUIDE.md and apply only if accepted below. Format: decision, reason.

- D-31 (accepted): Package names follow plan section 3.4 (app/e1_execution and so on). Reason: the plan, schema and slice prompts all use these names.
- D-32 (accepted): transition() publishes live updates after commit, and the pg_notify triggers of guide D-25 are not built. Reason: using both would send every event twice.
- D-33 (accepted): Liveness and heartbeat SQL uses clock_timestamp(), never now(). Reason: project rule, and now() stays frozen inside a transaction.
- D-34 (rejected): no MLE or OLE verdicts and no problems.memory_limit_mib; verdicts stay as the baseline defines them (per case AC, WA, TLE, RE in test_results; compile error and overall verdict in attempts.verdict; a memory kill is end_reason memory_limit with the job reason "failed: memory limit", and the killed case may record RE). Reason: keep the schema identical to the baseline and reduce risk.
- D-35 (PENDING, decide after the day 2 isolate check, before slice E1-3): sandbox is Docker (plan D-09) or isolate (guide D-19).
- D-01 (accepted): as written in plan section 17.1, a refused allocate writes the refused audit row and the admitted to queued transition in the same transaction, then commits. Reason: the "ROLLBACK; audit" of baseline §10 cannot keep the audit row in one transaction.
- D-36 (accepted): The == pins in requirements.txt and requirements-dev.txt were generated with pip freeze on Python 3.13.5 (Windows) and must be re-checked on the VM's Python. Reason: the build targets Linux or WSL2, where the Python version and the available wheels can differ.
- D-37 (accepted): docker-compose.yml publishes the database port on the loopback addresses only ("127.0.0.1:5432:5432" and "[::1]:5432:5432"). Reason: the database must not be reachable from other devices on the LAN (matches guide D-29); [::1] is included because localhost resolves to ::1 first on Windows, where psycopg waits for its connect timeout (130 s by default) before it tries 127.0.0.1.
- D-38 (accepted): scripts/reset_db.ps1 is the Windows PowerShell run command for the database: it pipes db/roles.sql, db/schema.sql and db/seed.sql into psql inside the compose service db with docker compose exec -T, so the host needs no psql; slice A-3 adds the data folders and capacity.py to it, as to scripts/reset_db.sh. Reason: the development machine runs Windows PowerShell, where the bash script cannot run.
- D-39 (accepted): slice A-2 builds db/seed.sql and db/invariants.sql together with db/roles.sql and db/schema.sql, as plan section 4 says; slice A-3 keeps seed_data/problems/12/, scripts/reset_db.sh and scripts/capacity.py. Reason: the schema tests need the seed, and the invariant query is the slice's acceptance check.
- D-40 (accepted): security fix to the plan's schema, with plan 4.2 updated to match: the four trigger functions that read or write tables run with search_path = public, pg_temp; EXECUTE on job_state_track() is revoked from PUBLIC; the engines get no sequence grants. Reason: the A-2 code review showed that orch_app could attach the SECURITY DEFINER job_state_track() to a temp table of its own and forge history rows, and that a temp table named job_state_history captured real history rows and could run SQL as superuser; temp tables could also fool the faculty and M1 checks, and USAGE on the sequences let any engine burn another engine's ids.
- D-41 (accepted): scripts/capacity.py opens its own psycopg connection from DATABASE_URL (orch_app) and runs every statement inside one transaction that starts with SET LOCAL ROLE e3_role and rolls back on any exception; nothing runs outside it. Slice A-4 replaces this connection with tx("E3"). Reason: plan 6.5 says capacity.py runs in tx("E3"), but tx() comes with slice A-4, and the 14.1 row lets A-3 start once A-2 is done.
- D-42 (accepted): the A-3 tests are tests/schema/test_seed_data.py and tests/schema/test_capacity.py, next to the four files of plan 4.6. Reason: tests/schema/conftest.py holds the database fixtures until A-4 moves them to tests/conftest.py, and plan section 13 names no A-3 test.
- D-43 (accepted): .gitattributes keeps *.sh and seed_data/** at LF on every checkout. Reason: with core.autocrlf=true (the Git for Windows default) a clone gets CRLF, which bash refuses and which no correct program output matches.
- D-44 (accepted): with GPU_MODE=nvidia, scripts/capacity.py --profile host stops with an error when nvidia-smi lists no GPU, instead of removing every GPU row. Reason: on the demo machine an empty list means a driver problem; a machine without GPUs uses GPU_MODE=none.
- D-45 (accepted): scripts/capacity.py gives nvidia-smi 10 s to answer and the database connection 10 s to open, then fails. Reason: a hung driver or an unreachable server must stop a reset with an error instead of hanging it; neither number is in the baseline (A-3 code review).
- D-46 (accepted): both reset scripts first run python -m scripts.capacity --check-database DB_NAME, which writes nothing and stops the script (exit 2) unless DATABASE_URL names that database; plan 4.5 and 6.5 updated to match. Reason: the scripts rebuild DB_NAME but capacity.py writes to the database in DATABASE_URL, so a mismatch rebuilt one database and rewrote the capacity of another (A-3 code review).
- D-47 (accepted): a failing after_commit hook does not undo the commit: tx() logs it (after_commit_failed, with the hook's name and traceback), runs the next hook and returns normally. Reason: the work is committed, so raising would make the caller redo it, and one failed push must not cancel the others; each hook, dispatch first, handles its own failure.
- D-48 (accepted): tx() commits only the transaction it opened while it is still healthy: if the body caught a statement error (chained as the cause, with its SQLSTATE) or sent COMMIT or ROLLBACK itself, tx() raises RuntimeError, rolls back and skips the hooks. An error the body must survive belongs in a savepoint (with cur.cur.connection.transaction():). Reason: psycopg sends COMMIT for a failed transaction and PostgreSQL answers ROLLBACK without an error, so the hooks would run for work that was never committed (the hand-sent COMMIT or ROLLBACK case came from the A-4 review).
- D-49 (accepted): init_pool() opens one probe connection with the 10 s connect timeout of D-45, then the pool, which checks each connection before handing it out; a second open pool is refused and close_pool() clears it. Reason: a bare pool only logs a wrong DATABASE_URL and times out after 30 s without the cause, which broke capacity.py's one-line error, and after a database restart it would hand out dead connections (A-4 incident pass).
- D-50 (accepted): FakeClock.wait() checks the fake time between waits of at most 5 ms on the event, and wait_for_waiters(n) returns once n threads have seen the current fake time and kept waiting. Reason: a threading.Event cannot wake a fake clock, so this is how a set() from another thread ends the wait at once while no fake timeout costs real time; the sync point keeps loop tests free of races.
- D-51 (accepted): make_job() in tests/helpers.py makes queued jobs only; for its INSERT alone it sets app.actor E2 and app.reason submitted transaction-locally, as E2's submit() will, and no test code changes a job's state. Reason: job_state_track() raises JT002 on INSERT too, and E2-1 (submit) and E4-1 (transition) come after A-4.
- D-52 (accepted): app/common/types.py defines SubmitRequest(workload_type, cpu_millicores, ram_mib, vram_mib, time_limit_s, problem_id=None, lab_session_id=None) and SubmitResult(job_id, state, need_class). Reason: plan 5.4 uses both and plan 5.3 never defines them; the fields are the POST /api/jobs body and its 201 reply in context §12.
- D-53 (accepted, proposal): QueueEntry(job_id, user_id, need_class, submitted_at, vector) is what E2Port.queue_view() returns. Reason: plan 5.4 names it without fields; these are the queue order of context §11 plus whose job it is and what it asks for.
- D-54 (accepted): app/common/events.py holds only the Hub protocol; the event builders come with slice E4-4. Reason: plan 5 gives no event fields, so builders written now would be guesses.
- D-55 (accepted): retrying() makes 3 tries in all (the first and 2 retries) and refuses more; each retry is logged as tx_retry and a give-up as tx_retry_exhausted. CLAUDE.md's "at most 3 times" means 3 tries. Reason: plan 5.1 and the 5.6 check ("retries 40P01 twice and then raises"); the owner's answer during A-4 planning.
- D-56 (accepted): every stub in tests/stubs.py calls assert_outside_tx() before it records a call, and the db fixture uninstalls its stubs afterwards. Reason: an engine that calls another engine inside its transaction then fails its own tests long before C-1 (invariant 3), and no later test sees stale stubs.
- D-57 (accepted): scripts/capacity.py write(database_url, rows) opens a pool of one connection, runs apply() in tx("E3") and closes the pool, which completes D-41; it refuses to run where a pool is already open. Reason: every statement now goes through tx() while the CLI and its 32 tests stay unchanged.
- D-58 (accepted): app/common/logging.py exports log with info, warning, error and exception(event, **fields), one JSON line per call; ts, level and event cannot be overwritten, and a traceback stays inside its field. Reason: plan 7.1, 8.3 and 10.6 call log.warning, log.exception, log.error and log.info in this form (A-4 review).
- D-59 (accepted): pyproject.toml points pyright at .venv ([tool.pyright] venvPath "." and venv ".venv"); pyright itself stays out of requirements-dev.txt. Reason: without it the CLI and the language server do not find psycopg, and no library is added without the plan.
- D-60 (accepted): tx() keeps its nesting flag in a per-thread cell and clears the cell of the thread that opened the transaction. Reason: a generator suspended inside tx() and closed on another thread (Starlette runs sync iterators on pool threads) would otherwise leave the opening thread refusing every later tx() as nested (A-4 review).
- D-61 (accepted): transition() refuses to run unless its Tx is inside an open transaction; runs set_actor and its UPDATE on a cursor of its own (the caller's result stays readable) inside t.savepoint() (D-67); turns only SQLSTATE JT001 into IllegalTransition; runs clear_actor after the savepoint has exited, on every path that leaves the transaction usable (on a lost connection the original error is re-raised instead); and registers the job_state push as a functools.partial, so a failed push is logged with its job. The trigger stays the only check of the 13 transitions. Reason: an illegal move must leave the caller's transaction usable (D-48); a check in Python would be a second copy that is race-free only with a locking read; psycopg's transaction() on a connection outside a transaction would BEGIN and COMMIT by itself; the own cursor, the lost-connection case and the hook name came from the E4-1 code review and incident pass.
- D-62 (accepted): the job_state event of transition() is extra plus type, job_id, user_id, state, reason and at, and those six keys win over extra (plan 7.1 spread extra last). Reason: the hub filters events by user_id (plan 7.3), so an extra key must never send an event to another user or misstate the move.
- D-63 (accepted): make_job(state) in tests/helpers.py reaches all 8 states through transition() on fixed legal paths (cancelled from queued, released after a completed run), each step in tx() of the engine that plan 7.2 names; assert_invariants(unallocated=...) excuses the missing_allocation rows of exactly the listed jobs and nothing else. This replaces the "queued only" part of D-51. Reason: allocated and running jobs cannot hold an allocation before E3-2, and test data must pass the trigger like real data.
- D-64 (accepted): JobState, a Literal of the 8 states, lives in app/e4_monitoring/state.py and types to_state and expected; actor is typed Engine (job_state_history.actor allows only E1 to E4); app/e4_monitoring and tests/e4 get no __init__.py in E4-1. Reason: pyright then rejects a misspelt state or actor at the call site, E4 owns the state model, and the public app/e4_monitoring/__init__.py of plan 3.4 comes with the E4 port.
- D-65 (accepted): transition() takes an optional keyword-only expected: JobState; the UPDATE then also requires state = expected, and a job that has moved raises IllegalTransition naming the actual and expected states, writes nothing, is logged and leaves the transaction usable. The five positional parameters stay as CLAUDE.md defines them. Reason: otherwise transition() judges only the committed state, so a cancel decided while the job was allocated succeeds as running to cancelled once E1 has started it, skipping the stop and confirm of context §9 (E4-1 plan review).
- D-66 (accepted): the development PostgreSQL of docker-compose.yml runs with fsync=off, synchronous_commit=off and full_page_writes=off, and CLAUDE.md gains "Machine limits": one pytest process at a time, subagents one after another, only the affected test files during development and the full suite once before a commit, no extra Docker images for verification, and a warning before a command that creates many databases or runs over 5 minutes. Reason: the laptop hung under load during the E4-1 review (bug check 0x1CA, two review agents and test runs at once); the three settings cut disk writes, a crash can then corrupt only the development database, which the reset script rebuilds, and they are never used on the demo machine.
- D-67 (accepted): Tx gains savepoint() in app/common/db.py, a context manager around connection.transaction() that drops the after_commit hooks registered inside it when it rolls back (by an exception or psycopg.Rollback), those of inner savepoints already released included; transition() uses it, and CLAUDE.md now says to take savepoints inside tx() only with t.savepoint(). This extends the Tx interface of plan 5.1 and supersedes the A-4 review's rejection of a savepoint helper as not needed yet. Reason: with a bare connection.transaction(), a caller savepoint that rolled back a transition() still published its event after the outer COMMIT, so the pages showed a move that never happened (E4-1 code review; approved by the owner at the review).
- D-68 (accepted): E3 keeps no resource id cache. snapshot() reads every resources row with queries.read_resources(), without a lock, in its own tx("E3"); E3-2's allocate() reads the ids the same way inside its own transaction, then runs its one lock statement on those ids and calls fit() only on the rows that statement returns. This replaces the startup cache of plan 6.1 and the passages that assume it: IDS in the allocate() code of plan 6.3, e3.load_ids() in the main.py sketch of plan 12.1, and "every GPU row by cached id" in the E3-2 prompt of plan 15.3. It is safe because capacity.py locks every resources row, never deletes the cpu or ram row and refuses to run while an allocation is open: the lock statement returns each row's latest committed version, a GPU row deleted between the read and the lock is simply not returned, and a GPU added in between is used from the next allocate(). Reason: scripts/capacity.py runs as a separate process and cannot reload a cache inside the server, so a cache could name deleted rows or miss new GPUs until a restart (the SUMMARY gotcha for E3-1, confirmed by the E3-1 code review).
- D-69 (accepted): placement.Row is a NamedTuple of the six columns of plan 6.2 in the same order, and snapshot() builds its Snapshot with placement.snapshot_of() from the same Row and free() as fit(); fit() and snapshot_of() raise ValueError naming a missing cpu or ram row, so a database whose capacity was never loaded fails loudly instead of showing zero capacity. The comparisons stay written twice, in fit() and in Snapshot.fits() of app/common/types.py, and tests/e3/test_placement.py checks on 1,000 seeded cases that the two agree on the same rows. Reason: E2 admits by Snapshot.fits() and E3 re-checks with fit(); if they disagreed, E2 would admit jobs that E3 refuses or never admit jobs that E3 would place, and zero capacity would hold every job without a word.
- D-70 (accepted): allocate() reads the job (state, time_limit_s, payload_path) after its lock statement and before fit(): a missing job raises NotFound and a job not in admitted raises IllegalTransition naming its state, both with nothing written and logged as illegal_transition; transition(expected="admitted") stays the atomic check. This supersedes "a job that is not admitted is rejected by the trigger (JT001)" in the test_allocate row of plan 6.6: such a call is refused before any write and never reaches the trigger. Reason: a repeated or concurrent second call for one job would otherwise charge capacity again and fail on allocations_one_open_uk as a raw 23505, or write a refused audit row for a job that has moved; every allocate() locks the CPU row before that read, so the second call waits for the first to commit and then sees it.
- D-71 (accepted): the capacity event (message 12, plan 10.4) is {type: "capacity", resources: [one object per resources row with resource_id, kind, gpu_index, total, reserved, allocated], at}, at being the database time of the job's move; allocate() builds it inside its transaction from read_resources() after its writes and publishes it after COMMIT, only when it commits (a refusal changes no capacity); release() in E3-3 does the same. Reason: plan 10.4 fixes only {resources, at}; every writer of resources (allocate, release, capacity.py) holds the CPU row lock, so the re-read is exactly the committed state, and at orders the events.
- D-72 (accepted): allocate() dispatches once per committed allocation, after COMMIT, through a partial whose repr names the job and the allocation, and its allocate log line is the first hook after COMMIT, so it never claims a commit that failed and a dispatch that hangs cannot hide it. A dispatch that raises does not undo the commit (D-47): the job stays allocated with its open allocation and no attempt. E1-2's dispatch must return at once (it runs on the admission thread) and end its own failed start (stop, confirm, release, requeue); an allocated job with no open attempt left by a crash or a raise is the startup reconciliation's (E4-7). A check for such jobs while the server runs needs a threshold, so it is only a proposal for E4-5. Reason: E3 cannot end the job itself: allocated moves only to running or cancelled, both E1's moves, and invariant 4 allows no release before a confirmed stop.
- D-73 (accepted): make_job(state) in tests/helpers.py gets allocated and running jobs a real allocation through e3 allocate(), loading the S0 capacity with scripts.capacity when resources is empty; completed, failed and released jobs hold nothing, as after a release; assert_invariants() loses its unallocated parameter, and invariant_violations() returns the rows for the one test that makes a bare admitted to allocated move. This replaces the excuse of D-63. Reason: the E3-2 gotchas of SUMMARY; test data now meets invariant 4 with no exceptions, and a finished job that still held its allocation would be a leak until release() exists (E3-3).
